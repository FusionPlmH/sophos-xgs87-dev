# 10 · 这台机器独特设计的最佳用法

> 🏷 **状态（2026-11-23 复核）**：💡 **设想** —— 但"共用基建"那一节已经全部落地了，
> 见 [09-remaining-work.md](09-remaining-work.md) 和 README 的能力表。
> **前提：两边都是 Debian 13，不装 OpenWrt。**

## 10.0 设计本质

XGS 87 不是一个"路由器"，而是**两台独立计算机 + 一块共享的交换芯片**：

```
┌───────────────────────────────┐        ┌───────────────────────────────┐
│ 节点 A：x86 (2C/4G/16G eMMC)  │        │ 节点 B：NPU (4C A72/2G)       │
│ • 通用 Linux，生态全           │  PCIe  │ • 4×1G + SFP，硬件交换         │
│ • 有 USB、SATA 控制器、串口     │◄──────►│ • 10G CPU 链路                │
│ • 没有网口                     │ 串口   │ • 有 crypto 扩展（AES/SHA）    │
└───────────────────────────────┘        └───────────────────────────────┘
```

**能同时利用两者的方案，才算"用对了"。** 只用一个节点，另一个就是浪费。

## 10.1 能力矩阵

| 能力 | x86 | NPU | 结论 |
|---|---|---|---|
| 通用软件/容器/生态 | ★★★★★ | ★★☆ | 应用跑在 x86 |
| 网络转发/交换 | ☆（无网口） | ★★★★★ | 网络跑在 NPU |
| 加密吞吐 | ★★★（AES-NI） | ★★★★（A72 crypto；EIP197 反而更慢） | 都行，VPN 优先 NPU |
| 内存/存储 | 4 GB / 16 GB | 2 GB / 7.3 GB | x86 更大 |
| 功耗/散热 | 高 | 低 | NPU 适合 7×24 |
| 可折腾性 | ★★★★★ | ★★★（要重刷） | 实验在 x86 |
| 串口/带外 | 有 COM5 | 有 ttyS2（从 x86 访问） | 互为主备 |

## 10.2 方案一：NPU 当路由 + x86 当服务节点（**现在就是这个**）

```
        Internet
           │ (SFP 或 LAN1 做 WAN)
    ┌──────┴────────┐
    │  NPU: Debian  │  路由、NAT、nftables、DSA 四口、WireGuard
    │  4×1G + SFP   │  p1-p4 / sfp 都是标准 netdev
    └──────┬────────┘
           │ vNTB（实测单流 1.2 Gbit/s、RTT 0.6 ms）
    ┌──────┴──────────────┐
    │  x86: Debian        │  Docker: AdGuard、Home Assistant、
    │  192.168.0.50      │  Prometheus+Grafana、Uptime Kuma
    └─────────────────────┘
```

- **NPU 干网络**：DSA 四口 + SFP，转发走交换芯片，CPU 几乎不参与。
- **x86 干服务**：不碰转发，2 核留给容器。
- x86 通过 `eth0.31`（VLAN 31 → NPU `p4`）挂在家里 LAN 里，**不需要额外的 USB 网卡**。
- 管理面独立走 `eth0.100`（VLAN 100 → NPU `p8`），把笔记本插到 `p8` 就能同时访问两台。

**已经做完的部分**（不再是设想）：DSA 九口、SFP 10G、vNTB、双 VLAN、DHCP。
**还缺的**：NPU 上真正的路由/防火墙配置（`nftables` + `dnsmasq`，或 `systemd-networkd` 全套）
—— 系统层面完全支持，只是我们没配，见 [09](09-remaining-work.md)"想用某个功能时才需要"那一节。

**瓶颈**：x86 访问外网走 vNTB，实测单流 1.2 Gbit/s。家用足够；要跑满 10G 就得让流量留在 NPU 里。

## 10.3 方案二：纯路由器（低功耗 7×24）

只开 NPU，x86 装个最小 Debian 或者干脆闲置（x86 断电不影响 NPU 启动）。

- 4×1G + SFP，空闲约 10–15 W。
- 适合当主路由/旁路由/实验室出口。
- 浪费了 x86 的 4 GB 内存和算力，但最简单、最稳。

**变体**：x86 平时休眠，需要时通过串口把 NPU 的控制台转出来。

## 10.4 方案三：x86 为主机，NPU 当"交换机 + BMC"

如果主要需求是**跑服务**而不是路由：

```
        Internet
           │
    ┌──────┴───────┐
    │ NPU: 纯交换   │  DSA 配好口，Linux 只跑串口代理/监控
    │ + 带外管理    │  串口代理、看门狗、远程重启
    └──────┬───────┘
           │ 用 vNTB 就够（不用再插 USB 网卡）
    ┌──────┴───────┐
    │ x86: 主服务器 │  Docker/KVM/Home Assistant/NAS
    └──────────────┘
```

- 早期设想是"给 x86 插 USB 千兆网卡接面板口"，**现在不需要了**：vNTB 已经能跑 1.2 Gbit/s，
  而且不像 USB 网卡那样多一个故障点。
- NPU 还能同时提供：串口代理（`ser2net`）、上电监控、交换机端口镜像。
- 注意：vNTB 走的是 NPU 的 CPU，重负载时占一个核；USB 网卡 + 面板口是交换芯片零 CPU 转发。
  **只有要跑满 1G 又不想吃 NPU CPU 时，那块 USB 网卡才值得插。**

## 10.5 方案四：网络实验平台 / IDS 靶场

- NPU 用 DSA 把 4 个口做成独立 VLAN/网桥（`ip link add ... type bridge` 即可，能力已具备）。
- 端口镜像：把 WAN 口镜像到 lan4，接一台机器跑 Suricata/Zeek。
- x86 跑流量生成（`iperf3`、`tcpreplay`）和日志分析。
- 优点：真实硬件交换，不是 veth，实验更接近生产。
- 需要：DSA 的 mirror 支持（`tc mirred` 或 `mv88e6xxx` 的 port mirror）—— **未验证**。

## 10.6 方案五：NAS / 媒体中心（受限于存储）

- x86 前面板 USB 是 **EHCI 2.0**（~40 MB/s），接 USB SSD 只能到 35–40 MB/s。
- 16 GB eMMC 做系统盘，媒体库放 USB 硬盘。
- 2 核跑 Jellyfin 软解勉强（1080p 可以，4K 不行，无 GPU）。
- 价值一般，适合"顺便"而不是主用途。

## 10.8 硬件增强（低成本高回报）

| 增强 | 效果 | 备注 |
|---|---|---|
| USB 千兆网卡（x86） | 1G 直连、不吃 NPU CPU | 只有在要跑满 1G 且不想占 NPU 时才划算 |
| USB SSD（x86） | 存储从 16 GB → TB 级 | USB2.0 限速 ~40 MB/s |
| Wi-Fi 卡（M.2/mini-PCIe） | 变成 AP | 参考机型有 QCA988x；本机需确认插槽 |
| SFP 模块 | 光纤/10G 上联 | 已实测 10G |

## 10.9 功耗与寿命

- 两颗 SoC 都是嵌入式低功耗型号，空闲估计 **10–20 W**。机箱**有**风扇，但软件控不了（见 [19](19-module-vs-kernel-rebuild.md)）。
- eMMC 写入寿命有限：日志/容器数据尽量放 tmpfs 或外部存储，开 `noatime`。
- NPU 的 RTC 没有电池时回 2105 年，日志时间不可信，建议 NTP 强制同步。

## 10.10 一句话总结

> **让 NPU 干它擅长的事（交换/转发/加密），让 x86 干它擅长的事（通用计算/容器），
> 中间用 PCIe vNTB 连起来。**

两台机器现在**都是 Debian**，方案一（NPU 当路由 + x86 当服务）的基建已经全部就位，
剩下的只是"要不要在上面配路由/服务"，而不是"能不能"。
